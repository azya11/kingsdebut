By M13, the repository should look roughly like this. You will build it up gradually — do **not**

```
kingsdebut/
├── main.go                 # wiring only: build the game, build the UI, run it
├── internal/
│   ├── chess/              # pure chess logic — imports NO Fyne, NO os/exec
│   │   ├── board.go        # board + piece types, starting position
│   │   ├── fen.go          # FEN parse / export
│   │   ├── move.go         # move type, make/unmake
│   │   ├── movegen.go      # pseudo-legal + legal move generation
│   │   ├── rules.go        # check, checkmate, stalemate, draws
│   │   └── *_test.go       # tests live next to the code they test
│   ├── engine/             # Stockfish process wrapper (UCI protocol)
│   │   └── uci.go
│   └── ui/                 # Fyne widgets and rendering
│       ├── boardwidget.go
│       └── assets/         # embedded piece images
└── docs/
    └── LEARNING_PLAN.md    # this file
```

**Why `internal/`?** Go treats a directory named `internal` specially: only code inside this
module can import it. It is the standard way to say "this is my implementation, not a public API."

**Import paths.** Your module is `kingsdebut.com/xo` (see `go.mod`), so the chess package is
imported as:

```
import "kingsdebut.com/xo/internal/chess"
```

**The one architectural rule that matters:** `internal/chess` must never import `fyne.io/...` or
`os/exec`. Chess logic that knows nothing about screens or subprocesses is testable, reusable, and
the reason your perft tests (M7) will be fast. If you ever feel tempted to break this rule, that
is the signal you need an interface instead (M9).

## M3 — Moves and pseudo-legal generation

**Goal.** Generate every move a piece could make ignoring check.

**Go concepts.** Methods with pointer vs value receivers (and when each is correct) · building
slices with `append` and pre-allocating with `make([]Move, 0, n)` · nested loops and early

**What you build.**
- A `Move` type. Minimum: from-square, to-square. Leave room for a promotion piece and flags —
  M5 will need them.
- `func (b *Board) PseudoLegalMoves() []Move` dispatching per piece type.
- Knight and king: fixed offset tables. Beware board-edge wraparound — this is the classic bug;
  think about how you detect that a move wrapped from the h-file to the a-file.
- Sliding pieces (bishop, rook, queen): loop outward along each direction until you hit the board
  edge, a friendly piece (stop before), or an enemy piece (include the capture, then stop).

**Acceptance criteria.**
- From the starting position, `PseudoLegalMoves()` returns exactly **20** moves.
- A test with a hand-placed lone knight on each of a1, d4, and h8 returns 2, 8, and 2 moves.
- A sliding-piece test confirms a rook stops before a friendly piece and includes an enemy piece.

**Self-check.**
1. When must a method use a pointer receiver, and what happens silently if it does not?
2. How does your code prevent a knight on h1 from "jumping" to a-file squares?

## M4 — Make/unmake and real legality

**Goal.** Filter pseudo-legal moves down to legal ones by rejecting moves that leave your own king
in check.

**Go concepts.** Pointers and mutation · copying structs (and why copying a `Board` containing an
array is cheap and safe) · `defer` · designing an undo record.

**What you build.**
- `func (b *Board) IsSquareAttacked(sq Square, by Color) bool` — the workhorse. Implement it by
  asking the reverse question from the square outward, rather than generating every enemy move.
- `func (b *Board) InCheck(c Color) bool` — find the king, ask if its square is attacked.
- `MakeMove` / `UnmakeMove`. Choose one strategy and be able to defend it:
  - **copy-make**: copy the whole board, apply the move, discard on undo — simpler, slightly slower;
  - **make-unmake**: mutate in place and store an undo record — faster, easy to get subtly wrong.
  Copy-make is the right choice while learning.
- `func (b *Board) LegalMoves() []Move` — generate pseudo-legal, apply each, keep only those that
  do not leave your own king attacked.

**Acceptance criteria.**
- Starting position still yields 20 legal moves.
- A test position with an absolutely pinned piece proves that piece cannot move off the pin line.
- A test position in check proves only check-evading moves are returned.
- After `MakeMove` then undo, `b.FEN()` equals the original FEN exactly. This is your safety net —
  every later milestone depends on it.

**Self-check.**
1. Why is *"does this move leave my king attacked?"* the only legality rule you need, rather than
   a separate pin-detection routine?
2. What does copying a `Board` copy, and what would it *not* copy if you added a slice field?
3. When would `defer` be the right tool for undo, and when would it bite you inside a loop?

**Ask Claude for.** Test positions (FENs) exercising pins and double check; review of your
attack-detection logic; help when your undo does not restore the FEN.

## M5 — Castling, en passant, promotion

**Goal.** Handle the three rules that break the "a move is just from-square to-square" assumption.

**Go concepts.** Bit flags and bitwise operators (`|`, `&`, `&^`) · encoding extra data in a
compact type · maintaining state invariants across make/unmake · edge-case-driven testing.

**What you build.**
- Castling rights as a 4-bit flag set on the `Board` (white kingside/queenside, black
  kingside/queenside). Rights are cleared when the king or the relevant rook moves *or is captured*
  — that last one is the commonly missed case.
- Castling legality: the king is not currently in check, does not pass through an attacked square,
  does not land on one, and all squares between are empty. `IsSquareAttacked` from M4 does the work.
- En passant: track the target square on the `Board` (FEN already carries it from M2). It is only
  valid on the immediately following move.
- Promotion: a pawn reaching the last rank generates **four** moves, one per promotion piece.
- Extend `Move` with the flags/promotion field, and extend make/unmake to handle the rook hop, the
  captured-pawn removal, and the piece swap.

**Acceptance criteria.**
- Make/unmake still round-trips the FEN for a castling move, an en passant capture, and a promotion.
- A test proves castling through an attacked square is rejected.
- A test proves castling rights are lost when a rook is captured on its home square.
- A pawn on the seventh rank generates four promotion moves, not one.

**Self-check.**
1. What does `flags &^ WhiteKingside` do, and why is it clearer than a subtraction?
2. Why must the en passant square be cleared after one move?
3. Which of these three rules changes the board in more than two squares, and what does that mean
   for your undo record?

**Ask Claude for.** The exact castling conditions restated; FEN test positions for tricky en
passant cases; review of your flag manipulation.

## M6 — Game outcomes

**Goal.** Detect checkmate, stalemate, and the draw conditions, so a game can actually end.

**Go concepts.** Maps (`map[K]V`), the comma-ok idiom, using a map as a counter · slices as
history · designing an enum for results.

**What you build.**
- A `Result` type: ongoing, white wins, black wins, draw — plus the reason for a draw.
- Checkmate: in check **and** zero legal moves. Stalemate: not in check **and** zero legal moves.
  Both fall out of M4 for free.
- Fifty-move rule using the halfmove clock you have carried since M2. It resets on a pawn move or a
  capture.
- Threefold repetition: hash or key each position and count occurrences in a
  `map[PositionKey]int`. The simplest key while learning is the position-only prefix of the FEN
  (placement + side to move + castling + en passant). Note honestly in a comment that this is
  slower than a Zobrist hash and why you chose it.
- Insufficient material: K vs K, K+B vs K, K+N vs K, K+B vs K+B with same-coloured bishops.

**Acceptance criteria.**
- Fool's mate reaches a checkmate result in a test.
- A known stalemate position returns stalemate, not checkmate.
- A test shuffles knights back and forth to trigger threefold repetition.
- A K vs K+N position reports insufficient material.

**Self-check.**
1. What is the comma-ok idiom and what is the zero value of a missing map entry?
2. Why must the repetition key exclude the move counters?
3. Why can a position be a draw with pieces still on the board?

**Ask Claude for. ** Clarification on the exact draw rules; sample mate/stalemate FENs; a review of
what your repetition key includes.

## M11 — Talking to Stockfish over UCI

**Goal.** Start the Stockfish binary as a child process and exchange UCI commands with it. Terminal
only at this stage — no GUI involvement.

**Go concepts.** `os/exec` · stdin/stdout pipes · `bufio.Scanner` for line-oriented reading ·
**goroutines** · **channels** · `context.Context` for cancellation and timeouts · `sync` basics ·
cleaning up a subprocess so it does not outlive your app.

**What you build.**
- `internal/engine/uci.go`: a type wrapping the process with `Start`, `Close`, and the UCI
  handshake (`uci` → wait for `uciok`, then `isready` → wait for `readyok`).
- A reader goroutine scanning stdout line by line and delivering parsed lines over a channel. This
  is your first real concurrency: the engine talks whenever it likes, and you must not block.
- `SetPosition(fen string, moves []string)` sending `position fen ... moves ...`.
- `BestMove(ctx context.Context, opts SearchOptions) (string, error)` sending `go depth N` or
  `go movetime N` and waiting for the `bestmove` line — honouring `ctx` cancellation so a search can
  be abandoned.
- `SetOption(name, value string)` for UCI options; `Skill Level` (0–20) and `UCI_LimitStrength` /
  `UCI_Elo` become your difficulty setting in M12.
- **Engine path must be configurable** — an env var, a flag, or a settings file with a sensible
  default. `stockfish/` is in `.gitignore`, so it will not exist on another machine. Never hardcode
  an absolute path.
- Reliable shutdown: send `quit`, wait, and kill after a timeout if it has not exited.

**Acceptance criteria.**
- A small test or `cmd/` program starts the engine, completes the handshake, sets the starting
  position, and prints a best move.
- Cancelling the context mid-search returns promptly with a context error rather than hanging.
- After `Close()`, no `stockfish` process remains in Task Manager.
- A missing or wrong engine path produces a clear error, not a panic.

**Self-check.**
1. Why does reading the engine's output need its own goroutine instead of a plain loop?
2. What is the difference between an unbuffered and a buffered channel here, and which did you pick?
3. What does `ctx.Done()` return, and how does your search loop notice it?
4. What happens to the child process if your program panics — and what did you do about it?

**Ask Claude for.** The UCI protocol explained (also see `stockfish/wiki/UCI-&-Commands.md` in this
repo); goroutine/channel concepts; help diagnosing a deadlock or a leaked process.

**Goal.** Play against Stockfish in your app without the window ever freezing.

**Go concepts.** Concurrency in a GUI application · why UI toolkits are not thread-safe ·

**Self-check.**

## M13 — Polish and packaging

**Goal.** Turn the working program into something you would hand to someone else.

**Go concepts.** File I/O and `os` · JSON encoding/decoding for settings · `flag` for CLI options ·
cross-platform paths with `path/filepath` · building and packaging a Fyne app for distribution.

**What you build.**
- PGN export of the finished game (headers plus SAN move text, both of which you have from M10) and
  optionally PGN import.
- Settings persisted as JSON: engine path, difficulty, board orientation, theme.
- First-run engine discovery: look in the settings file, then an env var, then `PATH`, then a
  bundled location — with a clear message and a file picker if none is found.
- Application icon and a real window title.
- Package with `fyne package -os windows -icon icon.png` and confirm the produced executable runs
  from a directory with no source code present.
- Rewrite `README.md` yourself: what the app is, how to build it, how to point it at Stockfish.
- Retire the now-dead `src/` and `render/` directories.

**Acceptance criteria.**
- The packaged executable runs on a clean directory, finds or prompts for the engine, and plays.
- Settings survive a restart.
- An exported PGN opens correctly in any chess viewer (lichess.org's import tool works).
- `go vet ./...` and `go test ./...` are both clean across the whole module.

## Testing discipline

- **Tests live beside the code**: `internal/chess/movegen_test.go` next to `movegen.go`, in the same
  package. You get access to unexported identifiers, which is what you want here.
- **Table-driven is the Go default.** A slice of case structs, a loop, `t.Run(tc.name, ...)`. You
  learned this in M2 — keep using it.
- **Perft is your ground truth** for M3–M7. Unit tests tell you a specific case works; perft tells
  you *everything* works. When a GUI bug appears after M8, run perft first: if it still passes, the
  bug is in the UI, and you have halved the search space for free.
- Useful commands:
  - `go test ./...` — everything
  - `go test ./internal/chess -run TestPerft -v` — one test, verbose
  - `go test ./internal/chess -bench=. -benchmem` — benchmarks with allocation counts
  - `go run -race .` — race detector, essential from M12 on

## Git rhythm

One commit (or a short-lived branch merged when green) per milestone:

```
git switch -c m3-movegen
# ... work, commit as you go ...
go test ./... && go vet ./...
git switch main && git merge m3-movegen
```

Commit messages that name the milestone (`M3: pseudo-legal move generation`) make your own history
readable later, and make it trivial to ask for a review of exactly one milestone's work.

## Known gotchas in this repository

- **`stockfish/` is gitignored.** It exists on your machine only. Any engine path must be
  configurable (M11) or the app breaks the moment it leaves this directory.
- **`xo.exe` is currently tracked** and shows up as modified on every build. Add it to `.gitignore`
  in M0 and untrack it.
- **Fyne needs CGO on Windows.** You need a working GCC (MinGW-w64 / TDM-GCC) on `PATH`. If
  `go build` fails with linker or `gl` errors, that is almost always the cause — not your code.
- **`README.md` is currently UTF-16 encoded** and renders as garbage. Rewrite it as plain UTF-8 in
  M13.
- **The `src` package name is not idiomatic Go.** Package names describe what is inside them
  (`chess`, `engine`, `ui`), never where they sit. This is why the target layout drops it.
